# 引擎可选安装（外部引擎扩展点）

> 状态：设计已定，尚未实现。
> 目标版本：0.9.87（待定）。
> 本文是给"以后接手的自己"看的工作笔记，不含任何本地路径、人名或凭据。

## 1. 为什么要做

现在的 43 个引擎全部编译进 `lib/engines/`，装插件就是装全部。由此有三个问题：

1. **体积只增不减**。每加一个引擎，所有用户都要下载它、加载它、审计它。
2. **加引擎必须我们自己发版**。第三方想接入，等于把维护责任转给我们。
3. **无法做"可选安装"**。用户不能"我不需要 Perplexity，就不要它"。

用户的原话意图：**「部分搜索引擎变成可选安装，可以不安装，可以安装」**，这样才能无限扩充引擎数量而不无限增大插件重量。

## 2. 分两期，先做第一期

| 期 | 内容 | 状态 |
|---|---|---|
| **第一期（本次）** | 加**外部引擎扩展点**，让一个第三方包能被发现、启用、参与搜索。现有 43 个引擎**完全不动**。用一个真实例子（Webz.io News Search）验证整条链路。 | 进行中 |
| 第二期 | 把现有 43 个引擎按需拆成独立包，核心包只保留注册表与最小内置集。 | 未开始，见第 9 节 |

先做第一期是因为：**拆包的前提是"引擎清单从编译期常量变成运行时注册表"**。第一期正好把这条链路走通并验证，再决定值不值得为拆包做完整重构。

## 3. 第一期范围（MVP）

| 能力 | 做不做 | 说明 |
|---|---|---|
| 包被发现（marker 字段） | 做 | 装完自动出现在设置页 |
| 设置页「外部引擎」列表 | 做 | 默认**不勾选**，不自动进白名单 |
| 勾选 → 进白名单 | 做 | 与内置引擎同一套 `allowedEngines` |
| 进回退链下拉 | 做 | 用户可拖进链里 |
| 显式调用 `engine: "<id>"` | 做 | `advanced_search` 等 |
| Multi **显式点名**（`engines: ["webz"]`） | 做 | 只换判据即可，不动池 |
| Multi **默认池**自动带外部引擎 | **不做** | 默认池来自 `languagePool()` → `normalizeLanguagePool()` → `ALL_ENGINES` 静态过滤 |
| 进语言池 `zhPool` / `enPool` | **不做** | 原因见第 5 节：静默失败，必须先做 `ALL_ENGINES` 动态化 |
| 进提示词引擎清单 | 不做 | 同上 |
| 进诊断报告 | 尽力 | 标 `source: external` |

> 注：早期版本这一行写的是「进 `multi_search` 并发池：做」，与第 5 节矛盾——multi 的并发池**就是**语言池。
> 实际边界是「显式点名可以，默认池不可以」。见 [external-engine-implementation.md](./external-engine-implementation.md) 第 0 节。

## 4. 契约（apiVersion 1，正式）

### 4.1 包怎么声明自己是引擎

引擎包在自己的 `package.json` 里写：

```json
{
  "name": "dsh-free-search-engine-webz",
  "version": "1.0.0",
  "dsh": {
    "freeSearch": "./lib/webz.js"
  }
}
```

`dsh.freeSearch` 是**指向入口模块的相对路径**。没有这个字段的包一律忽略。

### 4.2 入口模块导出什么

```js
export const freeSearchEngine = {
  apiVersion: 1,
  id: "webz",                          // 引擎 id，必须唯一
  label: { zh: "Webz.io 新闻", en: "Webz.io News" },
  time: true,                          // 是否支持时间过滤
  requiresKey: ["WEBZ_API_TOKEN"],     // 需要哪些凭据（我们负责解析）
  async search({ query, maxResults, timeRange, key, fetch, signal }) {
    // 自己发请求；只能拿到属于本引擎的凭据
    return {
      sources: [{ url, title, snippet, publishedAt }],
      truncated: false,
    };
  },
};
```

### 4.3 我们注入什么（安全边界）

| 注入项 | 内容 | 为什么不给更多 |
|---|---|---|
| `query` / `maxResults` / `timeRange` | 本次请求参数 | — |
| `key` | **只含本引擎 `requiresKey` 声明的那一个**凭据 | 不传完整 `cfg`：`cfg` 里有用户配置的**所有** API key，外部引擎能读走全部凭据 |
| `fetch` | 受控的 fetch（即 `proxyFetch`） | 复用搜索代理、`no_proxy`、超时；不给 `node:http` 原始能力也无意义（它能自己 import） |
| `signal` | 取消信号 | — |

明确**不给**：`cfg`、插件的设置写入能力、凭据中心。

### 4.4 发现规则

扫 profile 的 `node_modules` **顶层**（展开 scope 目录），逐个读 `package.json`，只认带 `dsh.freeSearch` 的。

- 不递归进嵌套 `node_modules`（那里有宿主内部包和自己的嵌套依赖，会误判）
- 不扫 `.pnpm`（内部结构，格式可能变）
- 跳过自身（`dsh-free-search`）

必须同时覆盖两种安装方式：

- `pnpm add` 装的 → 写在 `package.json`
- `pnpm link` 装的 → 常量 symlink，可能不写在 `package.json`

## 5. 为什么 MVP 不做语言池（重要，别忘）

池的校验在 `normalizeLanguagePool()`：

```js
.filter((engine) => ALL_ENGINES.includes(engine) && ...)
```

`ALL_ENGINES` 是 **`engine_meta.js` 的静态常量**，在 40+ 处被模块顶层求值。外部引擎的 id 不在里面 → **用户填了也会被静默丢掉**，然后回退到默认池。用户以为配好了，其实没有，且**没有任何提示**。

同类校验还有三处（白名单、回退链、池）。白名单/回退链的失败会「看得见」（勾了不生效、拖不进去），池的失败是静默的。所以池单独缓一期，等 `ALL_ENGINES` 彻底改成函数时一次做对。

**第二期必须先做这件事**：把 `ALL_ENGINES` 从常量改成 `allEngines()` 函数（`builtin + external`），并逐处过一遍 40+ 个调用点。

## 6. 安装界面（用户已提的问题）

用户问：「如何安装？得有一个界面，可以点安装按钮吧？要有进度条吗？是真实进度条吗？」

回答分三层，**第一期只做第 1 层**：

### 6.1 第一期：白名单区的形态（不是安装器）

设置页那块勾选网格按 6.1.1 分三段显示：主标题 `(a+c/b+d)`，下面 `内置 (a/b)` 与 `外部 (c/d)` 两小段。

- 默认**全不勾**
- 勾上 = 进白名单（与内置引擎同一套机制）
- 不勾 = 装了也不用（与 43 个中未启用的那些一样）

**这一期没有「安装按钮」**：安装靠命令行包管理器，我们不代劳。

### 6.1.1 内置与外部怎么分（白名单区）

白名单区是**纯勾选网格**，没有排序、没有拖拽，所以分段没有副作用。分三段：

```
全局启用的搜索引擎 (a+c/b+d)

  内置 (a/b)
  ☑ DuckDuckGo · HTML (FREE)   ☑ Bing (FREE)   ☑ Exa (FREE)  …（43 个，一格不少）

  外部 (c/d)
  ☐ Webz.io 新闻 (API KEY) · 需要 WEBZ_API_TOKEN · 正常
  ☐ 某某 (API KEY) · 加载失败：<原因>
```

规则：

- 主标题是 `(a+c/b+d)`：`a`=已启用内置、`b`=全部内置、`c`=已启用外部、`d`=已加载外部
- 两个小标题各带自己的 `(a/b)`、`(c/d)`，**不再重复"引擎"二字**
- 没加载到任何外部引擎时，外部那一段**整段隐藏**，主标题退化为 `(a/b)` 单段形式
- 外部引擎的网格里，每个格子后面挂状态：`正常` / `加载失败：<原因>` / `需要更新（apiVersion 不匹配）` / `未配置 key`
- 默认**全部不勾**；勾上才进白名单
- 计数只统计"已加载的"，配置里残留但没装包的 id 不进分母（否则分母虚高）

### 6.1.2 排序类区块（回退链 / 语言池）不分区

回退链与语言池是**带拖拽排序的单列表**。那里外部引擎与内置引擎混在同一个列表里，只加一个来源标记，不拆成两段——拆开会让"谁排第一"变成跨两个列表的拉锯。

所以：**分段只发生在白名单区（勾选网格），排序类区块只加标记。**

### 6.2 第二期：安装按钮

如果要"点一下装"，需要后端执行包管理器。设计要点：

- 走 bridge 路由（现有 `mutate` 那条通道之外新增一条）
- 执行 `pnpm add <pkg>`，**用 profile 目录做 cwd**
- 只允许安装白名单里的官方引擎包名（不允许任意包名，否则等于远程代码执行入口）
- 安装前给出「将执行什么命令」的确认

### 6.3 进度条（真实 vs 假）

**进度条不能是假的**。用户明确问了「是真实进度条吗」，这是在提醒不要糊弄。

实测（pnpm 11.21，`--reporter=ndjson`）：确实输出机器可读事件流，可用字段如下：

| 事件 `name` | 有用字段 | 能做什么 |
|---|---|---|
| `pnpm:stage` | `stage`: `resolution_started` / `resolution_done` / `importing_started` / `importing_done` | **阶段里程碑** |
| `pnpm:progress` | `packageId`, `status`: `resolved` / `found_in_store` / `imported` | **逐包计数** |
| `pnpm:fetching-progress` | `packageId`, `size`, `status`: `started` | 部分包大小 |
| `pnpm:summary` | 汇总 | 结束状态 |

**能做的真实进度**：

1. **阶段式**：resolution → importing → done，3~4 个里程碑，各阶段有明确文字
2. **计数式**：`X / Y 个包已导入`（累加 `pnpm:progress` 的事件）。这是真实数字，不是估算

**做不到的**：精确百分比。「已下载 37%」不在事件流里——`fetching-progress` 只报 `started`（带 `size`，但没有完成事件），且命中本地 store 时根本不下载。

所以结论：**做「阶段 + 包计数」，不做百分比**。并且明确告诉用户进度条的性质，不要画一个装模作样的百分比条。

如果实现时发现事件流不可靠（版本差异等），就退回「安装中…」+ 最终结果，**不做动画进度条**。理由：假进度条比没有更糟——它会在卡住时骗用户「马上就好」。

## 7. 隔离规则

| 情况 | 处理 |
|---|---|
| import 失败（语法错、缺依赖） | 记错误、跳过，启动不受影响 |
| `apiVersion` 不匹配 | 跳过，提示「该引擎需要更新」 |
| `id` 与内置 43 个重名 | **拒绝加载**，明确报错。不允许覆盖内置引擎 |
| 两个外部包同 id | 拒绝后加载的那个，报错 |
| `search()` 抛错/超时 | 当作普通引擎失败，进冷却，回退链继续 |
| 返回形状不对 | 丢弃本次结果，记错误 |
| 引擎不返回 `sources` 数组 | 同上 |

原则：**任何外部引擎的故障都不能拖垮整条搜索链**。

## 8. 断言计划

要能测外部引擎而不联网：

1. 假的引擎包（临时目录 + `package.json` 带 marker）= 能被发现
2. 无 marker 的包 = 不被发现
3. `apiVersion: 2` = 被拒绝
4. id 与 `bing` 冲突 = 被拒绝
5. 引擎抛错 = 记失败、链继续
6. 引擎返回坏形状 = 丢弃、记错误
7. 外部引擎不进默认白名单（装完不勾时）
8. 勾选后出现在 `allowedEngines`、能进回退链
9. 显式 `engine: "webz"` 能调用（走 runner 分支）
10. 注入的 `key` 只含声明的那一个（不泄漏其它凭据）
11. 注入的 `fetch` 是代理出口（能用 `no_proxy` 验证）

## 9. 第二期（拆包）备忘

真正实现"43 个引擎可选安装"需要：

1. `ALL_ENGINES` 常量 → `allEngines()` 函数（40+ 调用点）
2. `client.js` 第 1055 行那份**独立的静态 `ENGINES` 数组**改成从服务端拉（走 bridge）
3. `engine_meta.js` 的 `FREE_ENGINES` / `TIME_ENGINES` / `DEFAULT_FALLBACK_ORDER` 全部动态化
4. `assert-engine-modules.mjs` 的硬编码模块清单改成容忍外部
5. 决定核心包默认带哪些引擎（推荐：带 6 个免 key 引擎，保证装完能搜）
6. 每个引擎发包，命名约定 `dsh-free-search-engine-<id>`
7. 版本兼容：核心与引擎包的 `apiVersion` 对齐机制
